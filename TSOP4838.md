# TSOP4838 IR Receiver — Design Notes

A feasibility study and design document for adding an infrared remote-control
receiver ("driver") to avril, with lamp-box as the first consumer. Written
before any code, so that the design decisions — and their alternatives — are
recorded while the trade-offs are still fresh.

**Verdict up front:** the ATtiny85 is fully capable of this. It is, in fact, a
classic ATtiny85 application. The total effort is roughly a weekend: a few
hours for the code, and the rest is bench time tuning tolerances against real
remotes. The three genuinely interesting problems are (1) the millisecond
ticker is too coarse and needs a microsecond-resolution read, (2) RAM pressure
argues for decoding *in* the ISR, which deliberately bends avril's
"ISR notifies, main processes" contract, and (3) the power-down sleep gate
needs to learn about in-flight IR frames. Each is covered in detail below.

## 1. What the TSOP4838 actually does

The TSOP4838 is not a bare photodiode — it is a complete IR receiver front-end
in a three-pin package (Vs, GND, OUT). Internally it contains a PIN photodiode,
a ~56x automatic-gain-control amplifier, a bandpass filter centered on 38 kHz,
and a demodulator. All of the genuinely hard analog work — rejecting sunlight,
fluorescent-lamp flicker, and other continuous IR sources while recovering a
weak modulated signal across a room — happens inside the can.

What comes out is a clean digital signal:

- **Idle: HIGH** (the output has an internal ~30 kΩ pull-up, so no external
  pull-up is needed).
- **Carrier detected: LOW.** When the remote transmits a burst of 38 kHz
  carrier, OUT goes low for (approximately) the duration of the burst.

So from the MCU's perspective, "receiving IR" reduces to **measuring the
widths of pulses on one digital input pin**. That is squarely pin-change
interrupt territory — machinery avril already has.

Two datasheet details that matter to the decoder:

- **Pulse-width distortion.** The AGC and demodulator can stretch or shrink
  the output pulse relative to the actual carrier burst by up to a few carrier
  cycles — on the order of ±100–150 µs. Any decoder that measures *mark*
  widths must budget for this. (Section 4 explains how to sidestep it
  entirely.)
- **Supply filtering.** Vishay recommends an RC filter on Vs (≈100 Ω in
  series, ≥0.1 µF — 4.7 µF for noisy supplies — to GND). This matters here
  because the SK6812 strip shares the supply and draws large, fast-switching
  currents; without the filter, LED transients can appear as spurious pulses
  on OUT. Cheap breakout boards usually include it; a bare TSOP4838 needs it
  added.

Spurious pulses are never fully eliminated — ambient conditions can produce
occasional short glitches on OUT. The decoder must treat any out-of-window
timing as "reset to idle," never as an error to act on.

## 2. Is the ATtiny85 capable? The jitter budget

Yes — with one real hardware gap and a jitter analysis showing it doesn't
matter.

The gap: **the ATtiny85 has no input-capture unit.** On a larger part you
would route the TSOP output to ICP1 and let hardware latch the timer count at
each edge, giving cycle-accurate timestamps regardless of interrupt latency.
On the tiny85, timestamps are taken in *software*, inside the pin-change ISR,
so every source of interrupt latency becomes timestamp jitter.

The budget. NEC (Section 3) requires distinguishing intervals of 1125 µs from
2250 µs — the decision boundary sits ~560 µs from either nominal value, and
the protocol is conventionally decoded with ±25% windows (±280 µs on the
shorter interval). Against that budget, the jitter sources on this system:

| Jitter source | Worst case | Notes |
|---|---|---|
| `getMicros()` resolution | 8 µs | Timer0 counts once per 64 cycles at 8 MHz |
| ISR entry + prologue | ~2–4 µs | vector dispatch, register saves |
| `send_byte` cli window | ~11 µs | 8 bits × 10 cycles + entry/exit, at 8 MHz (see §8) |
| Ticker ISR running first | ~5–10 µs | short ISR, fires every 1 ms |
| Encoder/button ISR work ahead of the IR timestamp | ~15–25 µs | if sharing one ISR, take the timestamp *first* |
| **Total, everything colliding at once** | **~50 µs** | |

Worst-case ~50 µs of jitter against a ±280 µs window: comfortable, better
than 5x margin. The lack of input capture costs nothing here because the TSOP
has already slowed the signal down to protocol speed — the 38 kHz carrier,
which the tiny85 genuinely could not sample in software while doing anything
else, never reaches the MCU.

For calibration: whole commercial products (IR-controlled LED bulbs, cheap
media receivers) run exactly this arrangement on smaller processors
than an 8 MHz tiny85.

## 3. The NEC protocol

Nearly every cheap remote (and every "38 kHz IR remote kit" bundled with
hobby electronics) speaks NEC or its extended variant. Supporting NEC alone
covers the practical use case; other protocols (RC-5, Sony SIRC) could be
added later as sibling decoders but are out of scope here.

All marks are bursts of 38 kHz carrier at ~1/3 duty cycle; the TSOP outputs
LOW during a mark, HIGH during a space.

**Frame structure** (transmitted LSB-first, 32 data bits):

| Element | Mark (LOW) | Space (HIGH) |
|---|---|---|
| Header (AGC burst) | 9000 µs | 4500 µs |
| Bit "0" | 562.5 µs | 562.5 µs |
| Bit "1" | 562.5 µs | 1687.5 µs |
| Trailer | 562.5 µs | — (line idles HIGH) |

The 32 data bits are, in order: 8-bit **address**, 8-bit **~address**
(bitwise complement), 8-bit **command**, 8-bit **~command**. The two
complement bytes are free error detection: verify `command == ~invCommand`
and a corrupted frame is discarded with certainty rather than acted on.
(*Extended NEC* reuses the two address bytes as one 16-bit address with no
complement — so validate the command pair strictly and make the address
check optional/configurable.)

**Repeat codes.** While a button is held, the remote does *not* retransmit
the frame. It sends the full frame once, then every 110 ms a short repeat
frame: 9000 µs mark, 2250 µs space, 562.5 µs mark. The decoder reports these
as "repeat last command" — which is exactly what a lamp wants for
press-and-hold brightness ramping, and also what makes the system resilient:
if one frame is corrupted (see §8), the next repeat arrives 110 ms later.

**Total frame time:** 9 + 4.5 ms header + 32 bits (average ~1.7 ms each)
+ trailer ≈ **67.5 ms** for a full frame; a repeat frame is ~11.8 ms.

## 4. Design decision: decode on falling edges only

The naive decoder measures every mark and every space — 68 edges per frame,
each needing classification, and every *mark* measurement exposed to the
TSOP's ±100–150 µs pulse-width distortion (§1).

The better-known trick: **measure only falling-edge-to-falling-edge
periods.** Every NEC element begins with a mark, so consecutive falling edges
bracket exactly one (mark + space) pair, and the four possible periods are
cleanly separated:

| Falling-to-falling period | Meaning |
|---|---|
| 13500 µs | header of a full frame (9000 + 4500) |
| 11250 µs | header of a repeat frame (9000 + 2250) |
| 2250 µs | data bit "1" (562.5 + 1687.5) |
| 1125 µs | data bit "0" (562.5 + 562.5) |

This buys three things at once:

1. **Immunity to mark distortion.** If the TSOP stretches a mark by 150 µs, it
   steals exactly that much from the following space — the falling-to-falling
   *sum* is unchanged. The largest jitter source in the analog domain cancels
   out by construction.
2. **Half the work.** Rising edges are ignored (the pin-change interrupt still
   fires on them — PCINT cannot select an edge — but the ISR checks the pin
   level and returns immediately, ~10 cycles).
3. **Wider windows.** The smallest distinction is 1125 vs 2250 µs instead of
   562.5 vs 1687.5 µs; the decision boundaries move further from the noise.

Suggested acceptance windows (roughly ±20–25%, rounded to friendly numbers):

| Period read | Classified as |
|---|---|
| 900 – 1350 µs | bit 0 |
| 1900 – 2600 µs | bit 1 |
| 12000 – 15000 µs | frame header |
| 10200 – 11900 µs | repeat header |
| anything else | protocol violation → reset to idle |

These are starting values; §12's test plan includes printing raw measured
periods from real remotes to confirm the windows before trusting them.

## 5. Prerequisite: `Ticker::getMicros()`

The ticker's 1 ms resolution cannot distinguish 1125 µs from 2250 µs — a
one-tick measurement could be either. But the resolution already exists in
hardware and just isn't being read: Timer0 runs CTC at 8 MHz / 64 with
`OCR0A = 124`, so the live `TCNT0` value is a free sub-millisecond clock at
**8 µs per count**. Microseconds since boot:

```
micros = ticks * 1000 + TCNT0 * 8
```

(The constants generalize: `TCNT0 * prescaler / (F_CPU / 1_000_000)`, all
foldable at compile time from the existing prescaler-selection machinery.)

The subtle part is the classic `micros()` race, the same species as the
torn-read bugs fixed earlier in this repo: between reading `ticks` and
reading `TCNT0`, the compare match can fire. Worse, when called with
interrupts already disabled (from inside an ISR — the primary caller!), the
compare can fire and the tick ISR *cannot* run, so `ticks` is stale by one.
The fix is the standard one — after reading `TCNT0`, check the pending
compare flag; if it's set and `TCNT0` reads low (i.e., the counter already
wrapped), account for the millisecond that hasn't been added yet:

```cpp
uint32_t getMicros() {
    uint32_t ms;
    uint8_t  frac;
    ATOMIC_BLOCK(ATOMIC_RESTORESTATE) {
        ms   = ticks;
        frac = TCNT0;
#if defined(__AVR_ATtiny85__)
        if ((TIFR & (1 << OCF0A)) && frac < 250) {
#elif defined(__AVR_ATmega328P__)
        if ((TIFR0 & (1 << OCF0A)) && frac < 250) {
#endif
            ms++;
            frac = TCNT0;   // re-read: the wrap already happened
        }
    }
    return ms * 1000 + frac * 8;
}
```

Details worth recording:

- **The flag-register name differs per MCU** (`TIFR` on tiny85, `TIFR0` on
  328P) — one more `#if` pair in `ticker.cpp`, same pattern as the existing
  `TIMSK`/`TIMSK0` split.
- **Wraparound:** a `uint32_t` of microseconds wraps every ~71.6 minutes.
  All consumers must use the house-style wrap-safe subtraction
  (`now - then >= window` on unsigned values) — which the IR decoder does,
  since it only ever looks at deltas between consecutive edges.
- **Pause interaction:** `getMicros()` is only meaningful while the ticker is
  running. §9 covers what this means for power-down.
- **Cost:** ~20 lines in `ticker.cpp`/`ticker.hpp`, no RAM, and it's a
  generally useful primitive beyond IR (pulse measurement, servo timing,
  profiling).

## 6. The driver: `devices/IRReceiverNEC.hpp`

Shape of the API, following the conventions of `Button`/`RotaryEncoder`:

```cpp
namespace HAL {
namespace Devices {

template<uint8_t irPin,
         bool validateAddress = false,
         uint8_t expectedAddress = 0>
class IRReceiverNEC {
  public:
    void begin();   // setInput() (TSOP has its own pull-up), enablePCINT()

    // ISR context. Port-safe, same contract as the other devices:
    // ignores notifications for other ports and for other pins' edges.
    // NOTE: takes MICROSECONDS, not ticker milliseconds -- the ISR
    // passes HAL::Ticker::getMicros(), not getNumTicks().
    void notifyInterruptOccurred(uint32_t nowMicros,
                                 HAL::GPIO::Port port,
                                 uint8_t changed);

    // Main-loop context: claims a completed frame (atomically) and
    // dispatches the callback. Mirrors process() on the other devices.
    void process();

    // True while a frame is mid-flight. The main loop's power-down
    // gate must check this (see the sleep section of the design doc).
    bool busy();

    void setOnCommand(void (*cb)(uint8_t address,
                                 uint8_t command,
                                 bool isRepeat));
};

}
}
```

**The decode state machine** (runs in ISR context — see §7 for why) has three
states and fits in a handful of bytes:

```
IDLE ── falling edge ──► SYNC (timestamp it; nothing to classify yet)

SYNC ── falling edge, period ≈ 13500 µs ──► RECEIVING (bitCount = 0)
     ── falling edge, period ≈ 11250 µs ──► emit REPEAT, back to IDLE
     ── anything else ──────────────────► restart SYNC from this edge

RECEIVING ── falling edge, period ≈ 1125 µs ──► shift in 0
          ── falling edge, period ≈ 2250 µs ──► shift in 1
          ── 32nd bit shifted ──► validate cmd == ~invCmd;
          │                       if good: latch frame, set framePending
          │                       either way: back to IDLE
          ── out-of-window period ──► abandon frame, back to IDLE
```

Two robustness details:

- **Staleness timeout.** If noise produces a lone falling edge, the decoder
  would otherwise sit in SYNC forever, and `busy()` would block power-down
  indefinitely. The fix is cheap: since consecutive in-frame edges are never
  more than 13.5 ms apart, `busy()` (called from the main loop) treats a
  state older than ~20 ms as dead and resets to IDLE. No extra timer needed —
  it compares against the same `getMicros()` clock.
- **Repeat-code hygiene.** A repeat is only meaningful within ~120 ms of a
  full frame (or a previous repeat). A repeat arriving from a cold start —
  e.g., the first frame was corrupted, or the receiver woke mid-stream — is
  reported with `isRepeat = true` and the *last known* command; if there is
  no last known command, it is dropped. Callers that don't care simply ignore
  the flag.

**`process()`** is the same atomic-claim pattern as the debouncer redesign:
disable interrupts, snapshot-and-clear `framePending` plus the latched 32
bits, re-enable, then run the callback in main-loop context. Callbacks never
run in the ISR — that half of the concurrency contract is fully preserved.

## 7. Why the decoder lives in the ISR (the RAM math)

Avril's documented contract is "ISRs notify, the main loop processes" — all
state machines run in main-loop context. A contract-pure IR driver would have
the ISR only append `(timestamp)` records to a ring buffer and let
`process()` do the classification.

The arithmetic kills it. A full frame has 34 falling edges; storing periods
as `uint16_t` needs 68 bytes of buffer (plus indices). Current lamp-box RAM:
174 bytes data + 210 bytes bss = **384 of 512 bytes**, leaving 128 for stack
*and* any new feature. A 68+ byte buffer eats more than half the remaining
headroom for no functional gain — the classification work it defers is ~30
cycles per edge, trivially affordable in the ISR.

So the decoder state machine runs in the ISR, and the design accepts that
knowingly. The *reason* behind the contract still holds, though, and this is
the part worth being precise about: the rule exists to prevent state being
mutated from two contexts. The decoder's working state (`lastFallMicros`,
`accumulator`, `bitCount`, `state`) is touched **only** in ISR context; the
main loop touches only the completed-frame latch, and only under the atomic
claim in `process()` (plus the staleness check in `busy()`, which is
snapshot-compared the same way). One writer per datum, handoff through one
atomic gate. Total driver state: ~15 bytes.

The avril README's concurrency section should gain a paragraph documenting
this as the sanctioned exception pattern: *time-critical decoders may run
their state machine in ISR context, provided (a) their state is ISR-only,
(b) results cross to the main loop through an atomic claim, and (c) callbacks
still fire only from `process()`.*

## 8. Coexistence with the NeoPixel driver

This was initially misjudged in design discussion, so the corrected analysis
is spelled out with the numbers.

`send_byte` (in `lamp-box/src/neopixel-asm.S`) saves SREG, runs `cli`, bangs
out 8 bits at 10 cycles each, and restores SREG — **per byte**. Interrupts
are re-enabled between every byte of the pixel stream. So during a frame
render:

- **Worst-case interrupt blackout: ~11 µs** (≈86 cycles at 8 MHz), *not* the
  duration of the whole render. An IR edge landing inside a byte transmission
  is delayed by at most that. Against the ±25% windows this is noise (§2's
  jitter table already includes it).
- A full 32-pixel render is 128 bytes ≈ **1.4 ms**. During a 67.5 ms IR
  frame, at most two or three IR edges land inside any single render, each
  picking up ≤11 µs of delay. IR reception during animation *works*; frames
  are not corrupted by rendering.

The risk actually runs in the **other direction**: an ISR firing between two
pixel bytes stretches the strip's inter-byte LOW gap. If that gap exceeds the
SK6812's latch threshold (spec: ≥80 µs of idle latches the frame), the strip
latches mid-frame and displays one glitched frame. Current ISR worst case —
ticker ISR plus the full pin-change ISR back to back — is on the order of
25–40 µs; adding ~30 cycles of IR classification keeps it well under 80 µs.
Two rules keep it that way:

1. The pin-change ISR must stay lean; the IR decoder's per-edge work is ~30
   cycles and fine, but nothing heavier should creep in.
2. In the shared ISR, take the `getMicros()` timestamp **before** the
   encoder/button notification work, so encoder processing time never becomes
   IR timestamp jitter.

Residual truth: if a *render* and an IR *frame* and an *encoder twirl* all
collide pathologically, one IR frame can still be lost to timing corruption.
The complement-byte validation guarantees it is *discarded*, not misread, and
the remote's 110 ms repeat replaces it. The observable worst case is "held
button responds one repeat-period late while an animation frame was being
pushed" — acceptable by design, and worth a comment saying so.

## 9. Sleep and power-down interaction

Two separate cases, one clean and one needing a gate.

**Waking from PWR_DOWN (static patterns).** The lamp sits in power-down with
the ticker paused. The IR header's falling edge is a pin change → the chip
wakes (internal-RC startup is microseconds), the ISR runs `Ticker::resume(1)`
exactly as it does for encoder events, and the decoder timestamps the edge.
Here the falling-edge-only design (§4) pays off a second time: the first
edge's absolute timestamp doesn't matter — it merely *establishes the
reference point* — and every subsequent period is measured between two edges
taken on a running clock. The 9 ms AGC header exists in the protocol
precisely to give sleepy receivers a generous wake-up runway. Reception from
deep sleep works essentially for free.

**Going to sleep mid-frame — the real hazard.** The main loop's power-down
gate currently checks `pendingDebounceTimeout()` and `abortTxP`. Between IR
edges there are multi-millisecond quiet gaps (up to 13.5 ms in the header);
the main loop will happily run, find nothing pending, and pause the ticker to
power down. The next edge wakes it and `resume(1)` compensates *one* tick —
but the sleep lasted several milliseconds, so the µs clock has lost an
unknown multi-ms chunk and every period measurement in the frame is garbage.
The frame is then (correctly) discarded by validation, but reception during
sleep-heavy patterns would be near-useless.

The fix is the `busy()` predicate in the sleep gate:

```cpp
cli();
if (!reWithBtn.pendingDebounceTimeout() &&
    !irReceiver.busy() &&
    !abortTxP) {
    HAL::Ticker::pause();
    HAL::Sleep::goToSleep(SLEEP_MODE_PWR_DOWN);
}
else {
    sei();
}
```

Cost: the chip stays in IDLE (where Timer0 keeps counting) for the ≤70 ms an
IR frame is in flight, then resumes power-down. The staleness timeout (§7)
guarantees a noise edge can't wedge `busy()` on and silently ruin battery
life — the same failure shape as the stuck-interrupt-flag bug found in the
original debouncer, defended against the same way.

The IDLE frame-pacing path needs nothing: Timer0 runs in IDLE, `getMicros()`
stays valid, edges wake the loop. It already works.

## 10. Power budget

The TSOP4838 draws ~0.35–0.45 mA **continuously** — it must stay powered to
receive, and there is no useful duty-cycling scheme: an unpowered receiver
misses the header, and NEC gives no second chance within a frame. (Waking it
periodically to sniff for carrier costs more complexity than a lamp
warrants.)

For scale: the entire recent sleep-architecture effort drove the tiny85's
idle draw down to single-digit *micro*amps in power-down. Adding the TSOP
raises the floor by roughly **two orders of magnitude**; the receiver, not
the MCU, becomes the dominant idle drain. On a 2000 mAh battery, ~0.4 mA of
floor is ~200 days of standby — fine for a frequently-used lamp, but it
should be a *decision*, not a surprise. On wall power it is irrelevant.

If it ever matters, the honest options are: a physical power switch for the
receiver, or accepting encoder-only control on battery. Software cannot
recover this power.

## 11. lamp-box integration changes

*(lamp-box is a consumer that lives outside this repository — it's the
ATtiny85 SK6812 lamp in the parent `avrix` tree that motivated this
driver. This section is its integration plan, kept here because the
reasoning — ISR scoping, sleep gating, the pin-supply audit — is the
template any consumer will follow.)*

Beyond instantiating the driver, three concrete edits in `main.cpp`:

1. **Scope `abortTxP` to encoder pins.** The ISR currently sets
   `abortTxP = true` unconditionally on any pin change. With the TSOP on the
   same port, every IR edge — 68 per frame — would abort/blank the running
   pattern. The ISR must set it only for the encoder/button pins:

   ```cpp
   ISR(PCINT0_vect) {
       HAL::Ticker::resume(1);
       uint32_t nowUs = HAL::Ticker::getMicros();   // timestamp FIRST (§8)
       uint32_t now   = HAL::Ticker::getNumTicks();
       uint8_t current = PINB;
       uint8_t changed = current ^ previousPINB;
       previousPINB = current;

       irReceiver.notifyInterruptOccurred(nowUs, HAL::GPIO::Port::B, changed);

       if (changed & INPUT_PINS_MASK) {   // encoder + button only
           abortTxP = true;
           reWithBtn.notifyInterruptOccurred(now, HAL::GPIO::Port::B, changed);
       }
   }
   ```

   (`resume(1)` stays first so both clock reads are valid after a wake.)

2. **`irReceiver.process()` in `checkPeripherals()`**, and IR callbacks that
   map commands to the same handlers the encoder uses (`nextPattern`,
   `previousPattern`, per-pattern `onCW`/`onCCW` for held-button ramping via
   repeat codes). The command byte → action table is a `switch` learned from
   whatever remote gets used (§12).

3. **The sleep-gate `busy()` check** from §9.

Pin supply — checked, and it's tight but fine: the tiny85 has exactly five
usable GPIOs and lamp-box allocates all five (NEO on PB0, LED on PB1,
encoder A/B on PB2/PB3, button on PB4). However, `LED` is configured as an
output in `main()` and never driven afterward — it is free in practice, and
the TSOP takes its place on **physical pin 6 (PB1)**. The only alternatives
would be reclaiming PB5 by burning the RSTDISBL fuse (which costs normal ISP
programming — high-voltage programmer required thereafter; not worth it) or
moving to an ATtiny84. Losing an unused status LED is the easy call.

## 12. Development and testing plan

Protocol decoders are all about tolerances against real hardware, so the
plan front-loads visibility:

1. **Bring-up on the ATmega328P**, not the tiny85. Same avril code compiles
   for both, and the 328P has the now-trustworthy UART. Wire TSOP → any PCINT
   pin.
2. **Stage 1 — raw periods.** Before any state machine: ISR records
   falling-to-falling periods, main loop prints them. Point every remote in
   the house at it. This directly validates the §4 window table against
   reality (and immediately exposes non-NEC remotes, which will produce
   obviously different rhythms).
3. **Stage 2 — full decoder.** Print `address / command / repeat` lines.
   Hold buttons to watch the 110 ms repeat cadence. Build the command table
   for the chosen remote from this output.
4. **Stage 3 — torture.** Fluorescent/LED room lighting at close range,
   remote at max range and off-axis, rapid button mashing, two remotes at
   once. Assert: no *misread* commands ever (complement validation), only
   dropped frames.
5. **Move to the tiny85** in lamp-box. No UART, so acceptance is behavioral:
   remote control works during animations, from static (power-down) patterns,
   and while twirling the encoder mid-animation. The §8 collision case is
   checked by holding a remote button during the fastest pattern and
   confirming worst-case one-repeat-period lag.
6. **Regression:** confirm encoder/button behavior is unchanged, and that a
   night of idle on battery still shows power-down-level draw with the IR
   *decoder* idle (the TSOP's own 0.4 mA is expected per §10).
